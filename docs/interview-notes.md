# DurableFlow 面试追问笔记

> 用法：先自己答，再对照。答案都对应仓库里的代码，不要背成八股。
> 原则：先给结论，再说机制，再举项目里的例子，最后说取舍/限制。

---

## A. 数据库与并发

### 1. 为什么用 `FOR UPDATE SKIP LOCKED`？

多个 Worker 同时抢任务时，普通 `SELECT` 会读到同一行，导致重复执行。`FOR UPDATE` 锁住候选行，`SKIP LOCKED` 让其他 Worker 跳过已锁行，直接拿下一批。

代码：`app/worker/claim.py`。

取舍：SQLite 不支持 `SKIP LOCKED`，单测用进程内锁；生产必须 PostgreSQL。

### 2. 领取任务的事务为什么要短？

领取只是“把 PENDING 改成 RUNNING + 写租约”，应该立刻提交。如果在持有行锁时去解析 PDF 或调 LLM，其他 Worker 会被阻塞，连接池也会被占满。

代码：`claim.py` 只做 UPDATE；执行在 `executor.py` 里，且执行前先 commit。

### 3. 两个 Worker 会不会抢到同一行？

PostgreSQL 不会：`FOR UPDATE SKIP LOCKED` + 单条 UPDATE 是原子的。SQLite 单进程用一把锁；多进程 SQLite 不支持，所以生产用 PostgreSQL。

### 4. 数据量大了，`step_runs` 怎么优化？

- `idx_steps_claim (status, available_at)` 支持领取。
- `idx_steps_lease (status, lease_expires_at)` 支持 Reaper。
- 终态运行按时间归档/分区；UI 只查最近 N 条。
- 更彻底：按 `run_id` 分区，或把事件表写到单独的库。

### 5. 为什么状态用字符串枚举，不用数据库 ENUM？

字符串迁移成本低，跨 SQLite/PostgreSQL 方便；应用层用 `StrEnum` + 状态机校验。生产可以在 DB 加 CHECK 约束。

## B. 恢复与租约

### 6. Worker 执行到一半挂了，任务怎么恢复？

1. Worker 领取时写 `lease_expires_at`。
2. 执行中每 10 秒心跳续租。
3. Worker 挂掉后不再续租，租约过期。
4. Reaper 扫描 `RUNNING + lease_expires_at < now()`，重置为 `PENDING`，另一个 Worker 接手。

代码：`app/worker/lease.py`；演示：`scripts/crash_recovery.py`。

### 7. 租约设多长？太长/太短有什么问题？

项目默认 30 秒，心跳 10 秒。太短：正常的长步骤会被误判为死亡，导致重复执行；太长：Worker 挂了之后恢复慢。经验是“心跳间隔的 3 倍左右”，并且按步骤类型区分。

### 8. Worker 还活着但心跳丢了，另一个 Worker 接手，会重复执行吗？

会。这就是“至少一次”语义。解决方式不是保证不重跑，而是保证重跑不产生第二次副作用：`StepEffect` 唯一键 + Outbox + 业务幂等键。

### 9. 怎么区分“Worker 死了”和“任务只是慢”？

看心跳。只要心跳在续租，就认为活着；心跳停了才回收。所以心跳线程要独立于业务执行，不能被 LLM 调用阻塞。代码里 `LeaseHeartbeat` 是独立线程。

### 10. 时钟漂移会影响租约吗？

会。所有租约时间用数据库时间（PostgreSQL `clock_timestamp()`），不用应用服务器时间；多机部署时尤其重要。

## C. 幂等与一致性

### 11. 至少一次、至多一次、恰好一次的区别？

- 至少一次：可能重复，但不丢。
- 至多一次：可能丢，但不重复。
- 恰好一次：不丢且不重。跨系统外部副作用做不到字面恰好一次，因为“写业务库”和“发邮件/调第三方”不在一个事务里。

项目选择“至少一次 + 幂等”，这是工程上可落地的方案。

### 12. 怎么防止重复发邮件/重复扣款？

- 运行级：`Idempotency-Key` 唯一约束，重复请求返回同一个 run。
- 步骤级：`StepEffect` 表，`key = run_id:step_id:业务键`，唯一约束；第二次执行直接返回第一次的结果。
- 跨系统：Outbox + 消费端按 `event_id` 去重。

代码：`app/services/runs.py`、`app/agent/loop.py`、`app/core/outbox.py`。

### 13. Outbox 解决什么问题？不用会怎样？

业务写库成功后、发消息失败，会出现“库改了但事件没发”；先发消息再写库，会出现“消息发了但库回滚”。Outbox 把业务变更和事件写在**同一个数据库事务**里，relay 异步投递，至少一次；消费端去重。

### 14. Outbox relay 重发会不会重复？

会重发，所以消费端必须按 `event_id` 去重。Outbox 保证“不丢”，不保证“只发一次”。

### 15. 为什么说 Redis 锁不能作为正确性依赖？

Redis 主从切换、锁过期、网络分区都可能让锁失效；两个 Worker 仍可能同时执行。项目的正确性靠 PostgreSQL 行锁和唯一约束；Redis 只做租约提示、缓存和限流。Redis 挂了，任务不丢。

## D. 重试与失败

### 16. 哪些异常该重试？哪些不该？

- 该重试：超时、连接失败、429、5xx。
- 不该重试：参数错误、401/403、Schema 不匹配、业务规则拒绝。
代码：`app/core/retry.py` 的 `is_retryable`。

### 17. 为什么要加抖动？

大量任务在同一时刻失败，如果退避时间完全一样，会在同一毫秒一起重试，把刚恢复的服务再打垮。抖动把重试时间打散。

### 18. 重试次数越多越好吗？

不是。重试会放大成本、延迟和下游压力。项目默认 3 次，按步骤类型配置；超过上限进 `DEAD`，人工处理。

### 19. 毒消息怎么办？

必然失败的步骤在最大次数后进 `DEAD`，不会无限循环；提供手动重试 API。Agent 循环也有 `max_steps`。

### 20. 工具执行失败了，为什么不让异常抛穿？

抛穿会让整个步骤失败，模型看不到错在哪。项目把错误作为 `Observation` 回喂给模型，让它修正参数或换工具；连续失败 3 次才终止。

代码：`app/agent/loop.py`。

## E. Agent 与工具

### 21. Agent 的执行链路是什么？

`模型决策 → 解析 JSON → 工具权限校验 → 执行工具 → Observation 回喂 → 再决策 → 最终答案`。

代码：`app/agent/loop.py`。高风险工具在权限层直接拦截，返回 `pending_approval`。

### 22. 工具怎么注册？Schema 怎么定义？

`ToolSpec`：name、description、JSON Schema、permission、handler。注册表统一执行 `jsonschema.validate`。

代码：`app/agent/tools.py`。

### 23. 哪些工具只读、哪些能写、高风险怎么办？

权限分 `read / write / dangerous`。`dangerous` 没有审批直接抛 `ApprovalRequired`，由工作流创建审批记录；审批通过后重跑该步骤，`approved_tools` 放行。

### 24. 工具参数被模型写错怎么办？

JSON Schema 校验失败 → `ToolArgumentError` → 作为 Observation 回喂，模型修正；不会直接打崩步骤。

### 25. 怎么防 Prompt 注入？

没有 100% 防御。项目做三件事：

1. 高风险工具必须人工审批。
2. 工具参数 Schema 校验，不直接拼 SQL/Shell。
3. 模型输出只当数据，不当指令执行。

## F. 上下文与记忆

### 26. 上下文窗口怎么压？阈值怎么定？

`ContextManager` 先估算 token，超过 `CONTEXT_MAX_TOKENS` 就把旧消息压成摘要，保留 system 和最近 N 条；如果还超，先丢最旧的 recent，再截短摘要。

代码：`app/core/context.py`。

阈值不是拍脑袋：按模型上下文窗口留出输出空间，再用真实任务压测；项目默认 4000，可配。

### 27. 压缩以后重要信息丢了怎么办？

- 摘要提示词要求保留目标、约束、已确认结论、未完成事项。
- 最近 N 条消息原样保留。
- 关键事实写长期记忆，不依赖对话历史。
- 压缩事件写 `events`，可以审计“什么时候压的、压了多少”。

### 28. 长期记忆怎么存、怎么召回、膨胀怎么办？

存 `memories` 表：namespace、key、content、tags、importance、expires_at。召回用关键词 + importance/recency 排序；膨胀用 `compact`：保留高优先级，删除低优先级，生成一条摘要记忆。

代码：`app/agent/memory.py`。

### 29. 短期记忆和长期记忆怎么区分？

- 短期：当前 run 的 messages，随上下文压缩。
- 长期：跨 run 的 `memories` 表，按 namespace 隔离。
- 写入长期记忆要挑选：稳定事实、用户偏好、已确认结论；不要把每轮对话都写进去。

## G. 成本与模型

### 30. 百万 token 怎么计费？一次任务成本怎么算？

按模型单价：`prompt_tokens/1e6 * 输入单价 + completion_tokens/1e6 * 输出单价`。项目每次 LLM 调用写 `llm_calls` 表，记录模型、prompt/completion token、成本、延迟；运行汇总在 `workflow_runs.total_cost`。

代码：`app/llm/pricing.py`、`app/nodes/base.py`。

### 31. 不同业务怎么选模型？

按任务复杂度、上下文长度、成本、延迟、输出稳定性选：

- 分类/抽取：小模型 + 低 temperature。
- 复杂推理：大模型 + 思考模式。
- 高并发：便宜模型 + 缓存 + 短输出。
项目把模型配置放在节点级，运行级设 `max_cost`，超预算失败。

### 32. 成本超预算怎么办？

运行有 `max_cost`；每次 LLM 调用后累加，超过就抛 `NonRetryableError`，步骤失败，避免静默烧钱。生产可以改成暂停并告警。

## H. 观测与评估

### 33. 任务变慢，从哪里查？

先看分段耗时：`llm_calls.latency_ms`、步骤 `started_at/finished_at`、`step_duration_seconds` 直方图；再看队列深度、租约过期、重试次数。先判断是模型慢、工具慢、还是数据库/调度慢。

### 34. 为什么看 P95 而不是平均值？

平均值会被大量快请求掩盖长尾。用户感知和 SLA 通常看 P95/P99；项目 `metrics.py` 用 Histogram 记录步骤耗时。

### 35. 版本更新怎么证明效果提升了？

`scripts/compare_versions.py`：两版各跑 N 次，对比成功率、P50/P95、平均 token、平均成本。只有指标变好且样本量足够，才说“提升”；否则说“在这个场景下没有显著差异”。

### 36. 怎么证明没有重复副作用？

故障注入 + 数据库断言：同一个 `StepEffect` key 只允许一条；`send_email` 重跑返回第一次结果。测试：`tests/test_idempotency.py`。

## I. 系统设计

### 37. 为什么不用 Celery / Temporal？

- Celery 偏任务队列，缺少步骤级持久化状态机、人工审批、断点继续。
- Temporal 很强，但部署/学习成本高，个人项目容易变成“会调 API”。
- 这个项目用最小实现把 `SKIP LOCKED`、租约、幂等、Outbox 讲清楚。

### 38. 怎么扩容？

- 加 Worker；瓶颈通常在数据库连接/行锁、LLM 限流、下游工具。
- 按步骤类型拆分 Worker 池/队列。
- 终态数据归档；读走副本。
- LLM 节点做限流、缓存、预算。

### 39. 多租户怎么做？

- `workflow_runs` 加 `tenant_id`，所有查询强制带租户。
- 工具权限按租户配置；高风险操作审批人按租户。
- API Key/JWT + RBAC；审计日志。
- 当前项目只有可选 API Key，这是明确的限制。

### 40. 运行中动态加步骤怎么做？

当前规划器输出是数据，工作流步骤启动时固定。下一步：把 plan 持久化成 `step_runs`，在节点成功后根据 plan 释放/创建后续步骤；需要版本化和幂等，避免重复创建。

## 最后：主动说限制

面试官最怕候选人不知道边界。这个项目可以主动说：

- Agent 内部是步骤级恢复，不是消息级 checkpoint。
- 外部副作用是至少一次 + 幂等，不是字面 exactly-once。
- 单 PostgreSQL 主库，不做多活。
- 动态 DAG、RBAC、Grafana dashboard 还没做。

**能说清“还没做什么、为什么”，比把方案吹成完美更加分。**

## J. CTO 面 / 软性问题

### 41. 你为什么做 Agent / 后端，而不是只调模型？

不要答“因为火”。给一条具体的演进线：

> 我最早做电商运营，接触 AI 工具后发现它有时准、有时不准，但我说不清为什么。后来系统学 Python 和大模型应用，先做结构化抽取，再做 RAG，最后发现真正难的不是“把模型调通”，而是“让长任务在失败、超时、重启的情况下稳定跑完”。所以我做了 DurableFlow。对我来说，Agent 不是聊天框，是一套需要工程化的执行系统。

### 42. 你怎么看“全天候 Agent”（always-on）？

> 全天候意味着任务会长期挂着、随时触发、失败要能恢复，不能靠一个 HTTP 请求从头跑到尾。核心是持久化执行、租约/心跳、幂等、成本上限和人工兜底。我的项目就是按这个思路做的：状态落库、Worker 可恢复、危险操作审批、成本超预算中止。现在还没做的是消息级 checkpoint 和多租户，这是下一步。

### 43. 你和别的候选人有什么不同？

> 我不只是会调模型。我有企业知识库实习，做过数据采集、RAG 工具化、MySQL/Redis 缓存；也有从 0 到 1 的项目，能把评测、失败路径、成本、可观测性做出来。我的项目不是跟着教程跑的 Demo：我能说清每个数字怎么测的，也能现场杀 Worker 演示恢复。

### 44. 你能给公司创造什么价值？

用“问题 → 迁移 → 推进”三段：

> 我解决过的问题是“非结构化文档变成可检索、可追溯的知识”，以及“长任务失败后从头再来”。这两件事在很多企业场景都成立：合同/标书审查、客服知识库、内部流程自动化。如果让我负责一个方向，我会先找一条真实链路，定义成功指标（准确率、P95、单任务成本、人工介入率），先做小闭环，再补评测和可观测性，最后才扩场景。

### 45. 你怎么学习，才不会在 AI 时代被淘汰？

> 我不追每一个新框架，主要抓不变的部分：数据库、并发、分布式、评测、成本、安全；新模型和新框架用来替换某一层，不改变底层工程问题。我的习惯是看官方文档 + 做一个能跑的项目 + 用数据验证，而不是只看教程。

### 46. Claude Code / Codex / OpenHands 这些 harness 你怎么看？

> 我把它们当“开发效率工具”和“Agent 形态参考”，不神话。Claude Code/Codex 在我的工作流里主要用来读代码、改代码、跑测试；OpenHands 这类开源 harness 值得看的是它们的工具权限、沙箱、上下文管理和失败恢复设计。真正落地企业时，模型会换，但这些工程问题不会变。
