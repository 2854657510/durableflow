# 技术选型取舍

面试里比“用了什么”更重要的是“为什么不用另一个”。下面每条都给出当前选择、替代方案和适用边界。

## 1. 状态机 + Outbox vs Celery / Temporal

| 方案 | 能解决 | 不解决 | 结论 |
|---|---|---|---|
| Celery | 异步任务、重试、定时 | 步骤级状态机、人工审批、断点继续、步骤依赖 | 适合“发一封邮件”这类单任务，不适合长链路 |
| Temporal | 持久化工作流、重试、信号 | 部署和概念重；个人项目成本高 | 生产级选择，但本项目要自己讲清底层 |
| 本项目 | 步骤状态、租约、幂等、审批、Outbox | 分布式事务、跨区域多活 | 用 PostgreSQL 把机制做薄、做透 |

不是“Celery 不好”，而是这个项目的目的是展示**持久化执行**本身。用 Celery 会把最关键的部分藏进框架里。

## 2. SSE 用数据库轮询 vs Redis Pub/Sub

| 方案 | 优点 | 代价 |
|---|---|---|
| 数据库轮询（当前） | 无状态、天然多实例、断线按 id 续传 | 每连接每秒一次查询 |
| Redis Pub/Sub | 扇出快、空轮询少 | 消息不持久，断线期间的事件会丢；要自己做补发 |
| PostgreSQL LISTEN/NOTIFY | 事件驱动、少空轮询 | 连接占用、通知有丢失风险，仍需按 id 补查 |

当前选择优先**正确性和可恢复**：事件已经在 `events` 表里，SSE 只是读。规模上来后可以加 `LISTEN/NOTIFY` 或 Redis Stream 做唤醒，但事件表仍然是事实来源。

## 3. asyncio + Semaphore vs 线程池

- LLM 调用是 **IO 密集**，线程大部分时间在等网络；协程切换成本更低。
- 信号量限制在途请求，直接对应上游的并发配额/限流。
- 现有 Worker 和 SQLAlchemy 是同步的，所以异步批量模块保持独立：只在异步层发请求，结果回到同步层再落库，避免在事件循环里跑阻塞 SQL。
- 如果强行把整个 Worker 改成 async，要换 async SQLAlchemy、改测试和事务边界，收益不成比例。

## 4. Chroma vs pgvector vs Milvus

**本项目没有做三者的实测对比**，原因是本机 PostgreSQL 没装 pgvector 扩展，Milvus Lite 对 Windows 支持也不好。所以简历和面试里只说选型判断，不报没测过的数字。

| 方案 | 适合 | 不适合 |
|---|---|---|
| Chroma | 本地原型、单机、快速验证 | 大规模并发、强事务、多租户隔离 |
| pgvector | 已有 PostgreSQL、想少一个组件、数据量和并发中等 | 亿级向量、需要专用 ANN 调参 |
| Milvus | 大规模向量、独立扩缩容 | 个人项目运维成本高 |

选型顺序：数据量 < 100 万且已有 PostgreSQL → 先 pgvector；需要独立扩缩容 → Milvus；只做原型 → Chroma。真正上线前用同一批 query 做 Recall@K + P95 对比，而不是看 benchmark 截图。

## 5. Kafka vs Redis Stream vs RabbitMQ

本项目没有引入消息队列，因为 Outbox + Worker 已经能满足“至少一次 + 幂等”。如果要做“上传文档 → 解析 → 批量向量化”的独立链路：

- **Redis Stream**：已有 Redis，支持消费组、`XACK`、`XAUTOCLAIM`、死信，足够个人项目。
- **RabbitMQ**：路由和确认模型更成熟，但要多一个中间件。
- **Kafka**：高吞吐、可回放，适合日志/事件流；个人项目属于过度设计。

面试里如果被问 Kafka，应该能讲清分区、消费组、offset、至少一次和幂等的区别，而不是硬说项目用过。

## 6. RRF vs 加权融合

（标书平台）

- 加权融合要先把向量相似度和 BM25 分数归一化，再调权重；两路分数分布随 query 变化，权重很难稳定。
- RRF 只用排名：`score = Σ 1/(k + rank)`，不需要分数可比，参数少，跨 query 更稳。
- 代价：丢掉了“分数差多大”的信息；如果两路分数校准得很好，加权融合上限更高。

当前数据里，纯向量对招标编号 Top-10 召回 0/9，BM25 和 RRF 都能把正确块排到第 1；在这种“精确词命中”场景，RRF 的稳定性比调权重更重要。

## 7. LangGraph vs 手写循环

（标书平台）

- 固定流程（检索 → 抽取 → 校验 → 报告）用图：节点边界、状态流转、失败分支都显式，容易测试和画图。
- 开放探索（不知道要调几次工具）用循环：ReAct 的 `thought → action → observation` 更自然。
- 项目里两套都实现，用同一批问题对比，结论是“固定流程用图、开放探索用循环”，而不是二选一。
